Splunk 实现机制：领导主报告

1. 首先理解 Splunk 在解决什么问题

Splunk 的主要价值是把分散的机器数据转变成可查询、可关联、可持续运行的分析结果。放到 UEBA 场景，它需要依次回答：发生了什么、涉及谁、平时怎样、这次有什么不同、多个异常是否构成威胁、为什么应优先调查。

从公开架构和本地配置可以看出，这些能力由多个层次协同完成：底层保留和检索事件，中间统一数据语义与实体身份，上层产生行为信号、聚合风险并展示证据。某一层出现问题，后面的模型也可能产生看似精确但归因错误的结果。

对自研 UEBA 最有价值的认识，是将“数据事实、行为异常、安全判断、调查优先级”分开表达。登录失败是事实；登录失败次数高于个人历史是异常；失败后成功并新增管理员权限是需要解释的行为链；风险分只是帮助安排调查顺序。这四件事不能用一个分数代替。

3.1 数据进入：把记录变成可以分析的事件

【事实】Forwarder 负责采集和转发，Indexer 负责索引，Search Head 发起搜索并汇集结果。事件切分、时间戳解释等发生在解析阶段；字段别名、查表和不少字段提取可发生在搜索阶段。12

【解释】这种安排允许保留原始数据，在后续理解变化时重新提取字段。但时间戳、事件边界或入口过滤一旦处理错误，后面仅修改查询未必能修复。因此“先把日志存进来”还不是“数据可供 UEBA 使用”。

3.2 统一语义：让不同厂商的数据能进入同一条检测

本地 Zeek 插件直接展示了这个过程：源地址转换成 src，目的地址转换成 dest，连接事件通过 eventtype 和 tag 进入 Network_Traffic 模型。CIM 是字段与事件类别的约定，插件负责落实映射。L01L02L03L04

【解释】统一字段名只是第一步。例如 bytes_out 表示从哪个主体发出、是否包含 IP 头、是否有重复观测，都会影响“异常外发量”。字段名相同但含义不同，比缺字段更难发现。

3.3 识别实体：将一次行为归到正确的人和设备

【事实】独立 UBA 把账号关联到人员，解析 IP、主机名与用户的关系，并维护这些关系随时间的变化。17

【解释】“10.0.0.8 是张三”不能成为永久关系。DHCP、VPN、NAT、共享终端和服务账号会改变其含义。网络 UEBA 至少要区分人员、账号、设备、地址和会话；无法可靠识别人员时，可以先产生设备证据，而不是强行归给某个人。

3.4 比较基线：将“很多”转成“相对谁不正常”

【事实】ES 的本地 UEBA 知识对象包括摘要、合并、特征和评分搜索，KV Store 跟踪特征与关联实体。审计界面公开了稀有特征和个体基线两类观察方式。910

【解释】要判断“外发量大”，需要明确对象、时间窗、字节口径、历史样本和比较群体。研发人员与备份服务器应采用不同参照；同一个人在工作日白天和周末凌晨也可能有不同的正常范围。

3.5 从弱信号形成调查对象

【事实】ES 检测可输出 intermediate finding 或 finding，风险修饰把分数和描述关联到实体；finding-based detection 可以依据累计实体风险分组。13

【解释】单独一次罕见登录可能是出差，一次大量传输可能是备份。若两者发生在同一身份和合理时间范围内，并伴随新增权限或敏感资源访问，就更值得调查。RBA 的作用是让弱证据积累和关联，但累加本身不能证明因果关系。

3.6 让分析师看得懂、查得回

【事实】独立 UBA 的威胁详情关联异常和时间线；ES 的排除机制会影响风险数据模型、实体评分及相关检测。2015

【解释】生产价值来自“分数背后的证据可解释”。应能看到原始事件、归因理由、当前值与基线、触发规则、排除状态和版本。关闭案件与删除证据是不同操作；误报反馈也不是自动获得可信训练标签。

5. 风险体系中必须区分的三个量

量 含义 重要边界
单条风险贡献分 检测对某个实体贡献多少风险 不是统一的恶意概率

【解释】“按检测取最大值”使一个输入更关注检测多样性，但另外几个输入仍会被高频误报影响。因此不能声称 ERS 天然防刷分，更不能把任意五项加权平均包装成 Splunk 的原始算法。

【解释】自研时应明确哪些状态属于“原始数据”、哪些属于“控制配置”、哪些属于“运行中任务”。这些状态的恢复方法不同。增加 Kafka 副本并不自动保证模型状态或定时任务不会重复执行。

2. 接入与解析：哪些处理可以后补

2.1 最先确定事件边界和时间

【事实】索引前的处理包括事件切分、时间戳识别、默认元数据与特定索引时字段提取。搜索时可继续进行字段提取、别名、计算字段、查表、事件类型匹配和标签处理。2

【解释】假设一个 Java 堆栈应是一条事件，切成十条后会直接改变频次特征。假设日志是 UTC，解析成北京时间会使“夜间登录”发生系统性偏移。去掉敏感字段或入口丢弃事件之后，后续查询无法凭空还原它们。

数据项 在 UEBA 中的用途 常见故障
事件时间 _time 行为顺序、时间窗、历史基线 时区错误、设备时钟漂移
索引时间 _indextime 观察数据到达与积压 把迟到当作刚发生
host 事件来源上下文 把日志采集器当作行为设备

这里的故障和 UEBA 用途属于工程分析。元数据的存在不自动保证对应业务含义正确。

2.2 接入成功与业务完整是两套验收

【解释】一条记录被接收，只能证明传输链路至少处理了这条记录。还必须对比源端产出量、事件类型分布、解析失败、迟到分布和关键字段覆盖率。身份审计少采集一个事件类型，可能恰好让“权限变更”整类检测失效。

HTTP/API 输入、文件转发和消息重试机制的确认语义并不相同。本次未逐协议验证端到端 exactly-once，因此不作“Splunk 保证全链路不丢不重”的结论。自研的信号层应另行定义幂等键、补采和重放策略。

3. 索引存储：为什么不必每次扫描全部原文

【事实】Splunk 将压缩原始数据、指向原始数据的 tsidx 文件和元数据组织成 bucket；bucket 具有时间范围。常规存储存在 hot、warm、cold 等生命周期，SmartStore 的远端存储场景不应简单套用同一冷热目录理解。3

【解释】可以把一次查询理解为：先按时间和索引范围排除不相关 bucket，再利用索引定位候选事件，必要时读取原文并执行字段提取，最后计算结果。这是概念执行过程，不是对专有文件格式或每个优化器步骤的复现。

层次 保存什么 与 UEBA 的关系
原始事件 可回溯记录 说明信号从何而来；支持重新解析
基础索引 帮助查找事件的位置和字段/词项信息 减少查询候选范围
数据模型加速摘要 特定模型的字段化加速数据 多条检测复用相同标准化数据
行为特征或基线状态 按实体、时间、特征组织的派生值 减少反复处理长历史窗口
风险及案件数据 检测输出、聚合结果、处理状态 服务运营而不是替代原始日志

不能把 tsidx 直接称为 Elasticsearch 索引或某种通用列式数据库文件，也不能推断其未公开的编码、压缩算法和执行器实现。

3.1 保留周期为什么属于检测设计

【解释】原始日志保留 7 天，而模型比较 30 天历史时，必须有足够的历史派生状态；但有状态不等于能还原原始证据。若案件调查期长于日志保留期，后来可能只能看到“当时系统算出了什么”，看不到“事件究竟记录了什么”。

容量也不能仅按原始日志估计。摘要、副本、特征、模型、风险证据、检索缓存和回填临时空间都占用资源。每类数据都需要独立的保留、重建和恢复策略。

4. Schema-on-read 与 CIM：灵活性来自哪里

Schema-on-read 可理解为在读取和分析时解释部分字段。它不意味着完全没有 schema，也不意味着所有处理都发生在搜索时。Splunk 的索引时结构化提取与搜索时知识对象共同构成数据解释机制。2L01

【解释】标准化使规则可以面向“认证行为”而非某个厂商的原始格式，但不负责创造缺失信息。网络连接日志没有用户身份，字段别名不会产生可信用户；TLS 元数据没有文件内容，映射到 Web 或网络模型也不会得到敏感文档名称。

5. SPL 如何执行，为什么查询写法影响成本

SPL 采用管道表达处理步骤：筛选事件、提取字段、计算、聚合和输出。命令的执行属性决定工作能够在 Indexer 分散完成，还是需要把数据汇集到 Search Head。可分布式 streaming 与集中式 streaming 是不同类别；“streaming 命令”也不等于持续消费消息的独立实时系统。4

【示例】以下查询仅用于解释执行结构，未在 Splunk 上运行；假设索引、插件和字段都已经配置正确：

index=network sourcetype=zeek:conn earliest=-65m latest=-5m
| where direction="outbound" AND isnotnull(src) AND isnotnull(bytes_out)
| stats sum(bytes_out) AS outgoing_ip_bytes count AS connections BY src
| sort - outgoing_ip_bytes

从语义看，它计算一个固定历史窗口内各源地址的外发 IP 字节量。它不包含身份解析、个人基线或异常判定，也不能被称为完整的外泄检测。

【解释】越早限制索引、时间和候选集合，越容易减少后续处理量。全局排序、高基数聚合、复杂关联和大规模字段提取都可能增加内存或汇集开销。不能简单认为“加几台 Indexer，所有 SPL 就线性变快”；实际执行计划还需 Job Inspector 等运行证据确认。

5.1 普通查询、摘要和数据模型加速

【事实】Data Model Acceleration 为数据模型的字段建立额外 tsidx 摘要。它加速一组模型字段上的分析，与针对单条报表的预计算不同。tstats summariesonly=true 只读取已摘要部分，不返回未摘要数据。5

【示例】

| tstats summariesonly=true sum(All_Traffic.bytes_out) AS outgoing_ip_bytes
  FROM datamodel=Network_Traffic.All_Traffic
  WHERE earliest=-65m latest=-5m All_Traffic.direction="outbound"
  BY All_Traffic.src

这段示意假设数据模型已加速、字段有效且摘要覆盖了时间范围。它与上面的原始索引查询可能并非完全相同的数据集合，尤其当模型还纳入了其他来源时。验证时必须先统一范围。

【解释】摘要会把字段解释的计算成本提前付出，但也形成新鲜度问题。若摘要落后 20 分钟，使用 summariesonly=true 的查询可能很快返回少量数据，而不是显式报错。对安全检测来说，结果少不一定意味着行为少。

6. 搜索怎样成为持续运行的检测

【事实】本地 UEBA 的保存搜索不只有最后一条检测，还包含 summarization、consolidation、feature 和 scoring；宏与 KV Store 一起参与运行。9

【解释】其工程本质是具有依赖关系的派生数据流水线。可以用下面的依赖示意理解，而不能把示意中的具体顺序或周期当成厂商所有规则的实现：

可分析事件
   → 小窗口摘要
   → 按实体合并历史
   → 特征 / 历史状态
   → 当前行为评分
   → 输出信号

6.1 三种时间必须分清

时间 例子 决定什么
数据事件时间 09:40 发生传输 行为所属窗口
任务执行时间 09:50 运行检测 系统何时处理
基线截止时间 使用 00:00 前已完成历史 比较参考是否泄漏当前信息

【示例】每 5 分钟运行一次，读取 [now-10m, now-5m)，是在为到达延迟留缓冲。这种调度仍需补采处理：晚到 30 分钟的数据会错过正常窗口。若扩大查询窗口，又可能重复产出信号。

可以给自研信号定义 hash(检测版本, 实体ID, 窗口起点, 证据集合标识) 作为幂等键。回放时先更新已有信号而非再次加分。这是自研设计示意，不是 Splunk 已公开的幂等算法。

6.2 状态错位比单次失败更难发现

【解释】特征搜索使用今天的数据，而 scoring 搜索读到前天的基线，作业可能全部“成功”却给出错误结果。因此流水线健康不能只有成功/失败，还需要数据覆盖截止点、基线版本、输入分区及最后更新时刻。

修改字段映射后，也可能同时存在旧口径摘要、新口径原始搜索和旧基线。若没有变更边界，系统会把口径变化误判成行为变化。数据模型、特征与检测版本需要一起审计。

7. 高可用和扩展：副本解决什么

【事实】索引集群按 bucket 复制。Replication Factor 描述数据副本数量，Search Factor 描述可搜索副本数量，后者不能大于前者。可搜索副本包含用于查询的索引文件；只有原始数据的副本与可立即搜索的副本并不等价。6

【解释】容量规划要同时考虑正常查询与故障期间恢复。集群节点故障后补副本、重建索引或恢复摘要，都会与业务计算争用资源。副本也不是长期备份：错误配置、错误删除或污染状态可能影响多个副本。

7.1 一个仅用于量级沟通的容量例子

【示例】假定 20,000 EPS、每事件平均 800 字节，则原始输入为：

每日事件数 = 20,000 × 86,400 = 1,728,000,000
每日字节数 = 1,728,000,000 × 800 = 1,382,400,000,000
           ≈ 1.3824 TB / 日（十进制）
30 日原始输入 ≈ 41.472 TB

这不是磁盘需求，也不是 Splunk 官方性能数据。磁盘估计还需要实测压缩、索引、摘要及副本开销。CPU 和内存取决于字段提取、并发查询、实体与分组基数、模型和回算强度，不能从 EPS 单独推算。

行为状态还有另一种规模：实体数 × 特征数 × 时间分桶数。例如 10 万实体、40 个特征、30 个每日槽位就是 1.2 亿个特征槽位，尚未包含稀有值集合及多对多关系。不能因原始数据存储充裕就认为 KV 或特征层不会成为瓶颈。

8. 权限、变更与可观测性

【事实】ES UEBA 区分管理员、分析师及普通用户的知识对象访问；8.7 文档尤其限制特征、关联身份和资产集合的访问。9

【解释】画像本身比单条日志更容易暴露人员行为模式。自研权限需要作用于数据、模型状态、检测编辑、例外规则和案件，不能只限制仪表盘菜单。计划任务以何种身份访问哪些数据，也会改变检测覆盖。

应分别监控接入、解析、模型覆盖、特征更新、检测调度、信号产出、风险刷新和调查回查。对“没有告警”至少区分：正常无异常、没有输入、字段缺失、模型未成熟、任务未运行、摘要落后、权限不足、被排除。Splunk 的 UEBA 审计页提供了这种诊断方向，但具体自研指标仍需设计。10

9. 平台机制对自研的含义

能借鉴的是“保留事实、统一语义、复用计算、按实体组织状态、解释结果”的机制。是否实现通用 SPL、是否采用搜索引擎、是否引入流处理及独立特征存储，应由具体场景和测量结果决定。

本次证据不足以复现 Splunk 的 tsidx 二进制格式、完整查询优化器、云服务内部拓扑、全链路投递一致性及所有调度实现。它们是待单独验证的边界，不应在自研预算中被当作已经解决的问题。

2. 实体与画像：行为检测的计算主键

2.1 人、账号、设备、IP 和会话不是一回事

【事实】独立 UBA 会归一设备与域名，将 HR 数据识别出的账号关联到人，并维护 IP、主机名与用户的时间关系。17

【解释】同一人可能有普通账号和管理员账号；同一服务账号可能被多人使用；同一 IP 在一天内可能属于多个设备。若将账号名或 IP 直接作为永久人员 ID，个体基线、跨事件关联和风险评分都会产生偏差。

【示例】用于解释所需信息的实体关系结构：

person_id=P001
  ├─ account_id=域A:S-1-...，用途=办公
  └─ account_id=域A:S-1-...，用途=运维

关系 R001:
  account_id → device_id → ip
  valid_from=2026-09-10T09:00:00+08:00
  valid_to=2026-09-10T10:00:00+08:00
  evidence=VPN 会话 + 终端登录事件
  confidence=high

该结构不是 Splunk schema。它说明自研若要解释“为什么将此网络行为归给此人”，需要时间边界、来源和置信度。冲突时保留多个候选或仅归设备，比无依据地合并更符合证据。

【事实】8.7 知识对象页列出检测及对应的摘要、合并、特征和评分搜索；KV Store 记录特征值及关联身份/资产；宏封装映射、转换、特征计算和评分；Transforms 让集合可被 SPL 访问。9

【解释】这能证明它是多个知识对象协作的有状态检测体系。不能据此推定每条规则都使用相同的每日窗口、相同 KV schema，或同一种训练算法。特别是本次没有拿到 UEBA Content App 的内部保存搜索，不能将自行编写的 SPL 称作还原代码。

3.1 已公开的两类计算行为

【事实】本地 UEBA System 审计页公开：10

检测族 公开的行为 不能从页面得出的结论
Rare Device* 登录活动包含多个特征分；分越低越稀有；小于 0.002 的特征标为稀有；behavior_rarity 表示稀有特征数量 每个特征分必然是简单概率；所有 Rare 检测统一采用该阈值

3.2 不能把“有统计”理解成“不需要训练”

【事实】UEBA 检测基于学习的历史基线；官方表示可能最长需要 30 天才产出异常。该表述不是所有检测必须等待恰好 30 天，也不是所有模型统一使用 30 天窗口。814

【解释】频率表、历史分位数、滑动均值也需要累积数据并更新状态。“统计方法容易实现”不意味着没有冷启动、漂移、数据稀疏和基线污染问题。

3.3 云端与本地需要明确分界

【事实】8.5 的 findings 复核页明确写出：ba_test 对 UEBA 仅适用于云部署。本地不能直接照搬云端测试索引切换流程。14

【事实】ES 8.7 检测页说不能修改底层 SPL 或检测逻辑，且 UEBA 检测不支持 CIM entity zones；同版本知识对象权限页却授予管理员搜索、宏和集合写权限，甚至列出修改检测的角色条件。269

两页存在未解决的支持口径差异。报告分别记录“功能说明的限制”与“知识对象的权限能力”，不作“任何部署都不可编辑”或“管理员可以受支持地修改全部内置规则”的概括。需要在目标版本及应用包上由厂商或实测确认。

此外，普通 ES 资产/身份能力不能未经核实就外推为内置 UEBA 支持；尤其不能假设 entity zones 已解决其多租户同名实体隔离。

4. 把典型行为算法讲清楚

本节全部属于【示例】：用可计算的方法解释公开检测类别，未声称 Splunk 使用以下公式、参数或算法组合。

4.1 罕见目标：相对谁罕见

对账号 u 访问目的地 d，定义过去已完成历史窗口的访问次数 n(u,d) 和该账号总访问量 N(u)。一个平滑频率例子是：

p(d|u) = (n(u,d) + α) / (N(u) + αK)

K 是已定义的类别空间大小，α 是平滑参数。若没有定义新类别如何进入 K，这个公式还不是完整实现。频率很低可以表示稀有；进一步还需区分“个人新目标但同部门常见”与“整个群体都少见”。

假设员工第一次访问公司新上线的文档服务，个人频率为零，但同部门多数人都在访问；它与首次访问无人使用的外部存储具有不同解释。单条稀有信号应携带个人与群体参考、历史覆盖天数及首次观察时间。

4.2 流量异常：当前值与可比历史

对同一设备每天的外发 IP 字节量，可以用历史有效样本的高分位数 Q 作为阈值，或者用稳健离差：

m = median(历史有效日数值)
MAD = median(|x - m|)
z_robust = 0.6745 × (当前值 - m) / MAD

这只是候选解释方法。MAD 为零时必须退化处理，长尾分布可能需要对数变换；使用分位数时则要说明有效样本数与分位数算法。28 天历史并不意味着 28 个有效可比样本，节假日、缺报和设备离线需要区分。

特别要区分“零行为”与“未采到数据”：完整观测的一天没有外发可以是零；采集器故障一天应是缺失。错误补零会把未来正常流量变成异常峰值。

4.3 同伴组：解决群体参照，不消除偏差

【事实】独立 UBA 公开了 HR、OU、行为聚类和设备活动等同伴分组思路。Peer Groups 专页说明行为组使用登录、会话、AD 等活动；组按日更新，账号及设备组有数据资格条件。1819

【解释】组织组易解释但可能混入不同工作职责；行为组更贴近活动，却可能把多个同样受攻击的实体归为“正常同伴”。小群体、岗位迁移和集体上线新系统都会改变比较基准。

ES 本地规则名中的 by Company / by Business Unit 只能作为群体维度的线索，不能证明其使用了独立 UBA 的行为聚类算法，也不能断言个体与群体阈值必须同时满足。

4.4 时间与序列：顺序是额外的信息

【示例】“多次认证失败 → 认证成功 → 权限变化 → 外部传输”需要定义关联账号、会话或设备，规定顺序、最大间隔、跨日行为以及重复事件处理。仅统计同一天出现四类事件，不等于验证了这条序列。

序列窗口太短会漏掉慢速活动；太长会将无关正常事件连接起来。对共享 IP 仅按地址关联尤其容易误判。展示时间线有助调查，但有时间线并不表示底层检测真的执行了序列匹配。

4.5 多维机器学习：算法只是链路中的一部分

【事实】MLTK 的 fit 用训练数据产生模型，apply 将已学习模型应用到后续搜索结果；这类命令有自己的预处理和运行限制。23

【解释】是否采用聚类、密度或其他异常算法，应首先看输入特征是否稳定。将访问量、目的地数量、夜间占比直接混合而不处理量纲、缺失和重尾分布，得到的距离可能只是数据尺度差异。

机器学习输出需要保留模型版本、训练范围、特征版本和解释依据。文档列出某个 MLTK 算法，并不意味着 ES UEBA 或独立 UBA 的某个具体模型正在使用它。

5. 独立 UBA：流式模型、批量模型和分析存储

【事实】UBA 5.4.0 架构文档公开管理、流式与批量三类逻辑角色。管理侧列有 UI、Job Manager、PostgreSQL、Impala 等服务；流式侧列有 Kafka、Redis 等；批量侧列有 Spark 和 HDFS。各节点的实际服务组合随部署规模变化。16

【解释】这里的意义是区分低延迟处理和长历史计算的资源形态，而不是给自研列一张必须全部采购或部署的组件清单。该文档也不足以精确指认每一种对象保存于哪个内部表或数据库。

5.1 从原始事件到分析视图

【事实】UBA 可通过 Direct connector 接收 Splunk 侧解析数据，也可用 Raw Events connector 交给 UBA 原生解析器。解析与实体处理后，按数据类型组织相关字段，存入 data cubes；模型基于聚合数据进行分析。17

【解释】所谓 cube 可以理解为按某些维度和粒度组织的分析数据，而不是“必须是某种固定 OLAP 产品”。聚合使模型不必每次处理全部原文，但丢失的明细必须能够通过原始数据或关联证据补查。

5.2 四类模型不是四套互斥算法

文档分类 主要职责 输出
Streaming models 面向新事件和较短窗口处理，保留时序相关状态 异常、IoC、分析数据
Batch models 对聚合历史及滑动窗口训练、评分或重算 异常等结果
Security analytics models 补充安全上下文及异常重评分 安全分析信息、调整结果
Threat models 综合数据与异常形成具体威胁 威胁对象

【事实】这些分类来自 UBA 模型文档；所有 threat models 被描述为批量模型。部分用例同时使用流式候选识别和离线异常生成。18

【解释】所以“UBA 支持实时流式分析”不等于“所有最终威胁实时出现”。计算延迟必须拆到信号、威胁与界面显示三个阶段测量。

6. 从 anomaly 到 threat：第二层安全判断

【事实】UBA 将 threat 定义为构成具体安全用例的一条或多条 anomaly，并可关联 IoC 与支持证据。公开路径包括 kill-chain、graph-based、data-driven 和 rule-based。17

路径 公开机制的含义 自研时需要额外明确的语义
Kill-chain 对同一用户或设备的异常寻找攻击阶段模式 阶段是否必须有序、缺失阶段如何处理
Graph-based 按类似异常群体计算，不限于单个用户或设备 节点、边、时间、权重及高频公共节点处理
Data-driven 综合异常及实体数据判断威胁 特征与模型、阈值、解释和校准
Rule-based 指定时间窗内满足自定义异常组合条件 去重、事件复用、升级和案件合并

右栏是设计分析，不是已经公开的 Splunk 参数。

6.1 横向移动模型的具体例子

【事实】独立 UBA 横向移动模型使用内部活动数据，文档列出 AD、防火墙和终端来源；默认使用 30 天活动数据，可配置，并结合同伴活动与安全规则降低误报。其详情展示涉及设备、威胁关系及异常时间线。20

【解释】这说明一个“模型”可能已经包含数据融合、统计行为、规则和证据组织，并不是单个数学函数。其 30 天配置仅适用于这个模型，不应成为所有 UBA 或 ES UEBA 的统一参数。

6.2 图关联不等于风险无条件传播

【示例】员工甲和乙都访问了同一域名，可在调查图中产生关联。但若该域名是大型云服务公共入口，这条边的区分能力很弱。将甲的风险自动传播给乙，需要额外规则和证据，不能仅由“共享对象”得出。

同样，ES threat topology 的展示机制与独立 UBA graph-based threat computation 是两个不同概念。拥有关系图 UI 不证明使用了图神经网络，更不能从图展示反推模型算法。22

7. ES 的 RBA：风险证据如何组织

7.1 风险对象、修饰和发现

【事实】风险修饰将实体字段、类型、分值和描述关联起来。检测可选择生成 finding 或 intermediate finding；可以对多个实体分别配置，也可以输出零分上下文。风险消息支持引用事件字段，threat object 可记录域名、哈希、命令行等关联对象。13

【解释】一个原始事件可能产生用户和设备两份风险贡献。此时按人员、设备或全局做统计必须明确口径，不能将多实体表达误当成多条独立攻击证据。

7.2 风险因子：把上下文作用于分值

【事实】ES 风险因子的公开公式为先加后乘：21

calculated_score = (base_score + Σaddition) × Πmultiplication

风险因子可以依赖实体属性或风险字段。文档指出总风险通过 Risk Data Model 动态计算，因此查询 index=risk 的基础分不一定等于采用风险模型得到的调整后分数。

【示例】某外发异常基础分 20，命中一个 +5 因子和一个 ×1.5 因子，调整后为 37.5；另两条独立贡献为 30、25，则示例累计值为 92.5。小数如何显示或取整，应在目标实现核实。该值不是 ERS，也不是 92.5% 的恶意概率。

因子越多不一定越准确。多个因子若表达同一业务事实，乘法叠加可能重复放大。上下文属性变更后的历史评分是否重算，必须与证据快照和审计口径一起设计。

7.3 从累计风险形成调查对象

【事实】finding-based detection 可以用累计实体风险阈值组织 finding group。13

【示例】上面的 92.5 若超过某自定义阈值 80，并且涉及至少两类独立行为，就可以生成“疑似外泄”调查对象。阈值、多样性条件和场景名称是示例，不是 Splunk 默认值。

总分只是聚合条件之一。确定性的高危行为可以由 event-based detection 直接输出 finding，不必等累计分。反过来，大量低质量风险条目累加到阈值也不自动具备高可信度。

8. ERS：实体综合排序，公开公式的边界

【事实】ES 8.5 ERS 对过去 7 天至少出现一条 intermediate finding 的实体计算 0–100 分，计划搜索 Risk - EWA Entity Risk Score Calculation 默认每 20 分钟执行。页面公开五个输入组件，但未公布具体权重和完整归一化细节。12

对调整分集合 s1…sn，可将公开输入写为：

C1 = Σsi                         总风险贡献
C2 = max(si)                     单次最大贡献
C3 = count(si ≥ 50)              高分发现数量
C4 = n                           发现总数
C5 = Σd max(si | detection=d)     各检测最高贡献之和

这是对公开输入的数学转写，不是完整 ERS 计算式。不能直接将 C1～C5 按任意权重平均后声称获得了同样的实体分。

【解释】C5 能反映检测多样性，但 C1、C3、C4 仍与事件频率相关。要证明抗重复能力，必须用同一证据重放、单规则高频噪声以及多规则同源命中的测试，观察最终分数和调查输出，而不是根据组件名称下结论。

8.1 ERS 再触发检测的注意事项

【事实】官方允许使用 ers 索引结果创建检测。27

【解释】这为“按实体整体风险升级”提供接口。但若升级结果又作为相同来源的风险贡献进入下一轮计算，可能出现自我放大。自研必须明确派生关系、哪些信号参与评分，以及如何避免聚合结果重复作为基础证据。官方提供接口不等于公开证明所有自定义闭环都安全。

9. 调优、排除和生命周期

【事实】Finding exclusion 作用于指定检测的 intermediate findings，并从 Risk Data Model 及相关 UEBA/风险视图中排除；可指定结束时间或无限期生效。15

【解释】这不等于删除原始日志。若自研或自定义检测绕过风险模型，直接读取原始 risk index，可能没有遵循同一排除口径。排除应记录来源、范围、原因及到期，且复核它究竟影响信号生成、计分、显示还是三者。

操作 应区分的含义 混淆后的问题
抑制通知 仍保留事实，只减少重复提醒 被误认为风险已消失
排除风险贡献 特定信号不参加评分 与裸索引查询结果不一致
关闭调查 工作流结束 被误认为原始证据应删除
调整分数 修改优先级计算 掩盖错误检测而非修复原因
更新基线 改变未来比较参考 恶意行为被学习成正常

【事实】ES 支持人工正负风险条目，进行一次性调整。13 【解释】负分本身也有时间窗生命周期；不能把“添加负分”视为永久清除某条历史风险。自研若使用此机制，应保留对冲对象和失效条件。

1. 与现有项目的关系

现有《UEBA 异常检测实现设计》已经区分确定性规则、基线偏离、异常组合、行为序列、统计/机器学习及风险评分，并覆盖身份、主机与网络数据；《网络流量与 UEBA 异常行为检测清单》等资料也梳理了流量侧场景。L07L08

4.1 是否复刻通用查询语言

实现完整类 SPL 平台会扩展到解析器、优化器、权限、分布式执行、知识对象和兼容性。若产品只支持限定防泄密场景，可使用受控检测定义；若分析师需要自由探索，则通用查询能力价值更高。该判断属于产品范围选择，不能仅由“Splunk 有 SPL”得出。

4.2 是否引入复杂模型

多维模型可能发现单一阈值遗漏的组合，也可能增加调试、样本需求和解释成本。个体统计能快速解释偏离，但会面对冷启动、小样本和角色变动。两者均需以真实业务误报样本和已知攻击样本验证，不以算法名称判定先进性。

4.3 是否把风险分作为主要入口

实体风险排序适合分析师主动调查，场景案件适合明确行动和闭环，直接告警适合确定性高危条件。可以并存，但必须避免同一行为在多入口被重复派发并重复计分。对用户呈现哪一种，应结合运营团队分工。

Windows AD 与 Zeek 日志采集机制对比

1. 结论先行

采集 Windows AD 日志时，Splunk Universal Forwarder（UF）通常部署在域控制器或 Windows Event Collector（WEC）服务器上。UF 通过 Windows Event Log 输入订阅事件日志通道，读取新产生的事件，保存采集检查点，再将事件发送到 Splunk Indexer。

这与 Zeek 采集的核心差异是：

  • Windows AD 安全审计使用 WinEventLog:// 模块化输入，通过 Windows Event Log API 读取事件通道；
  • Zeek 使用 monitor:// 文件输入，跟踪 conn.log、dns.log 等文件的增长与轮转；
  • 两者后续都会添加 host、source、sourcetype 等元数据，经 outputs.conf 发往 Indexer，再由对应 Add-on 完成字段标准化和 CIM 映射；
  • AD 事件日志、AD 目录对象变化和 AD 健康状态是三类不同数据，不能只启用 Security 日志后就认为已采全 AD 数据。

2. Windows AD 有哪些不同的数据来源

3.1 Windows 先负责产生事件

UF 不会自动让 Windows 生成所有安全事件。域控制器必须启用相应的高级审核策略；部分目录访问事件还依赖对象上的 SACL。若 Windows 没有生成某类事件，Forwarder 无法补出该事件。

例如，UEBA 常用事件可能包括：

行为 常见事件 ID 示例
登录成功、失败、注销 4624、4625、4634
使用显式凭据、特殊权限登录 4648、4672
新进程创建 4688
用户账号创建、启停或修改 4720、4722～4726、4738

本地域组成员变化 4732、4733

事件 ID 只能说明事件类别，具体行为还要结合 Subject、Target、Logon ID、源地址、工作站、组 SID、对象 DN 和结果字段解释。不同 Windows 版本、审计策略和事件提供程序会影响实际字段。

3.2 UF 订阅事件日志通道

本地 Splunk_TA_windows 11.0.2 的默认配置包含以下模板，但默认均为关闭状态；实际修改应放在 local/inputs.conf，不直接编辑 default/inputs.conf。本地 inputs.conf

[WinEventLog://Security]
disabled = 0
start_from = oldest
current_only = 0
evt_resolve_ad_obj = 1
checkpointInterval = 5
renderXml = true
index = wineventlog

参数含义：

参数 作用 需要注意
disabled=0 启用输入 TA 默认模板通常是 1，安装 TA 不等于已经采集
start_from=oldest 没有既有检查点时从较早事件开始 首次上线可能产生大量历史回补和延迟
current_only=0 允许读取已有历史事件 与 start_from、既有检查点共同影响起点
checkpointInterval=5 周期性保存读取检查点 这是检查点刷新配置，不是“每 5 秒才采一次日志”的简单轮询结论
renderXml=true 以 XML 格式采集事件 本地 TA 会将 XML sourcetype 归一并提取字段
evt_resolve_ad_obj=1 尝试解析 AD 对象信息 会增加域控查询或解析开销，应结合负载测试
index=wineventlog 指定目标索引 Indexer 必须预先存在该索引及权限配置

Splunk 官方说明 WinEventLog 输入针对本地 Windows 系统。采集远端事件更常见的做法是在目标主机部署 UF，或者先由 WEF 汇总到 WEC，再在 WEC 上部署 UF。Windows Event Log 官方说明

3.3 检查点与重启恢复

UF 保存每个事件日志输入的读取状态。正常重启后，它依据检查点继续读取，而不是无条件从 start_from=oldest 重新发送所有事件。start_from 主要影响没有有效检查点时的初始位置。

这不等于端到端业务层面绝对不重不丢。仍需考虑：

  • Windows 事件日志覆盖速度是否快于 UF 恢复速度；
  • 首次回补旧事件时新事件是否出现较大延迟；
  • UF 到接收端中断期间的本地队列和磁盘容量；
  • Indexer 接收确认、重试及下游检测是否具有幂等性；
  • 管理员清空日志、事件通道损坏或检查点被删除的情况。

繁忙域控制器首次从 oldest 回补可能造成采集积压。Splunk 官方故障排查建议根据需要仅采近期日志、从 newest 开始，或减少采集事件范围，但这些选择会改变历史完整性，必须在上线方案中明确。事件索引延迟说明

3.4 UF 添加元数据并转发

outputs.conf 的工作方式与 Zeek 主机上的 UF 相同：定义一个或多个接收端，由 UF 将采集到的事件发送给 Indexer 或中间 Forwarder。

[tcpout]
defaultGroup = splunk_indexers

[tcpout:splunk_indexers]
server = 10.10.10.21:9997,10.10.10.22:9997
autoLB = true

autoLB=true 表示在多个接收端之间分配转发流，不表示同一事件主动复制到每台 Indexer。索引集群的数据副本由索引集群机制负责。

Windows 事件通常带有：

host       = 产生或承载事件的 Windows 主机
source     = WinEventLog:Security 或 XmlWinEventLog:Security
sourcetype = WinEventLog:Security 或 XmlWinEventLog:Security
index      = wineventlog（示例）

使用 WEF 时要额外保证 host 最终表示事件原始主机，而不是全部显示为 WEC 收集器。当前 TA-Windows 为 ForwardedEvents 配置了主机覆盖逻辑。本地 props.conf

3.5 Indexer 和 Search Head 如何处理

当前本地 TA-Windows 对 XML Windows 事件配置了 XML 字段提取，并把不同来源归一到兼容的 XmlWinEventLog:* / WinEventLog:* sourcetype。部分高基数字段可以调整为搜索时提取，以权衡索引空间与查询成本。本地 props.conf

典型字段随后被映射到 CIM：

SubjectUserName / TargetUserName → user、src_user 或目标账号字段
IpAddress / WorkstationName      → src、src_nt_host
Computer                         → dest 或 dvc
EventCode                        → signature_id / 事件分类
NewProcessName                   → process_name
TargetSid / MemberSid            → 用户或组标识

具体映射随 EventCode 和 TA 版本变化，不能仅根据字段名称统一套用。Authentication、Change、Endpoint 等 CIM 数据模型会消费这些标准字段，供 ES 和 UEBA 检测使用。

4. WEF 集中采集模式如何工作

DC1 ─┐
DC2 ─┼─ Windows Event Forwarding ─→ WEC / ForwardedEvents
DC3 ─┘                                   │
                                  UF + TA-Windows
                                  读取 ForwardedEvents
                                         │
                                         ▼
                                      Splunk

在这种模式下，Windows 自己先通过 WEF 把多个域控或成员服务器的事件汇聚到 WEC。UF 只需在 WEC 上订阅 ForwardedEvents：

[WinEventLog://ForwardedEvents]
disabled = 0
start_from = oldest
current_only = 0
checkpointInterval = 5
renderXml = true
host = WinEventLogForwardHost
index = wineventlog

当前 TA-Windows 明确要求 WEF 采集采用 XML 格式，并通过 WinEventLogForwardHost 触发主机还原转换。Splunk 9.1 以后还需让 wec_event_format 与 WEF Subscription 的 Content Format（Events 或 RenderedText）一致；多个格式不同的 Subscription 不宜混入同一目标通道。inputs.conf 参考

二者没有脱离约束的绝对优劣。选择前应实测事件量、域控负载、允许安装代理的范围、网络隔离、WEC 高可用和故障恢复时间。

5. AD Monitor 不是 Security 日志输入

如果 UEBA 需要完整的用户、组、计算机属性和对象变化，可以单独配置 AD Monitor：

[admon://domain_directory]
disabled = 0
targetDc = dc01.example.com

该输入只能在 Windows 上运行；执行监控的主机需要属于目标域或林，并具备读取目录的权限。它可以运行在 Windows Splunk 实例或 Forwarder 上，再把数据发送给 Linux Indexer。官方建议谨慎配置对象路径和目标 DC，参数大小写也有明确要求。AD Monitor 官方说明

Security Event Log AD Monitor
审计事件流 目录对象状态与变化
依赖审核策略和 SACL 依赖目录读取权限和 LDAP 可达性
适合回答谁在何时执行了什么 适合补充用户、组、计算机及属性上下文
可用于行为序列和安全检测 可用于身份画像、组关系及富化

实际部署仍要验证 AD Monitor 是否满足所需历史语义。用当前目录快照富化过去事件，可能把今天的部门或权限错误地套到过去。自研 UEBA 应对重要身份属性保存有效时间。

8. 上线验证清单

  1. 在 Windows 事件查看器确认目标事件确实产生，再检查 Splunk；不要先把没有事件归因于 UF。
  2. 检查每台 DC 或每个 WEF Subscription 的事件量、最后事件时间和延迟。
  3. 验证 host 表示原始事件主机，尤其是 ForwardedEvents。
  4. 对比 EventCode、EventRecordID、Computer、Subject/Target、SID、IP 和 Logon ID 与原始 XML。
  5. 验证 UF 重启、网络中断、Indexer 切换后是否漏采或重复。
  6. 测试日志接近覆盖上限、WEC 积压和首次历史回补。
  7. 检查 TA 版本、XML/RenderedText 格式和 WEF Content Format 是否匹配。
  8. 分别验证 Authentication、Change、Endpoint 数据模型的事件覆盖和字段完整性。
  9. 对 4624/4625、4720～4729、4756/4757、4662、4688、1102 等实际需要的事件建立覆盖率监控。
  10. 记录输入配置版本、检查点状态、最后成功事件时间和数据缺口，供 UEBA 判断“零行为”还是“未采到”。
