# Splunk 机制到自研 UEBA 的映射与验证边界

## 1. 与现有项目的关系

现有《UEBA 异常检测实现设计》已经区分确定性规则、基线偏离、异常组合、行为序列、统计/机器学习及风险评分，并覆盖身份、主机与网络数据；《网络流量与 UEBA 异常行为检测清单》等资料也梳理了流量侧场景。[L07](<../../UEBA 异常检测实现设计.md>)[L08](<../../网络流量与UEBA异常行为检测清单.md>)

因此，本报告不再预设另一套替代架构，而将 Splunk 的可核实机制映射成需要回答的产品和工程问题。以下所有自研结构、公式、测试阈值及数据例子均是分析或示例，不代表领导已选定方案，也不代表 Splunk 原始实现。

## 2. 按证据能力划分场景，而不是按产品检测数量

| 场景 | Zeek 可以贡献的证据 | 补充数据 | 结论边界 |
|---|---|---|---|
| 异常外发量 | 连接、方向、字节、时间、目的地址 | 设备身份、业务角色、批准服务目录 | 可判断传输异常，不能仅凭流量确认敏感内容 |
| 首次或罕见外联 | 目标 IP、DNS、可见 TLS/HTTP 元数据 | 威胁情报、域名分类、业务白名单 | 首见只表示观测范围内首次 |
| 账号失陷 | 部分协议认证、异常连接行为 | IdP/VPN/AD/MFA 与终端登录 | 加密网络通常无法覆盖完整身份活动 |
| 横向移动 | 内部访问、扫描或协议活动 | AD、终端进程、权限变化、会话审计 | 横向访问行为与攻击横移并不等价 |
| 文件外泄 | 部分文件协议与传输关联 | 文件访问、代理上传、DLP、终端文件证据 | 加密链路上的文件身份通常需其他来源 |
| USB 拷贝 | 普通网络流量不能直接观察本地 USB 操作 | 终端设备与文件审计 | 不可因某厂商有 USB 检测就认为 Zeek 可覆盖 |
| 打印异常 | 网络侧可能只见打印连接 | Windows PrintService/打印服务器 | 作业数、页数和人员归属要依赖对应日志 |
| 邮件泄密 | 可见邮件协议元数据，受加密与部署限制 | 邮件平台审计、附件信息、DLP | 外发数量不等于敏感附件泄露 |

这些是由可观测性推导的场景边界。Splunk 的已验证来源页也说明本地 UEBA 涉及认证、终端、邮件等多种模型，不能把全部内容当作纯网络能力。[11](https://help.splunk.com/en/splunk-enterprise-security-8/administer/8.6/user-and-entity-behavior-analytics/ueba-detections-in-splunk-enterprise-security/required-sourcetypes-for-ueba-detections)

检测条目数量会受用户/设备、公司/业务单元等维度展开影响。同一个算法模板可以产生多条内容；反过来，一个“横向移动模型”也可能整合多阶段逻辑。对标单位宜是“数据要求＋判定逻辑＋输出证据＋已测效果”，而不是规则名数量。

## 3. 一条防泄密链路的可复核数据示例

### 3.1 观测与关系

虚构输入如下；地址使用文档示例网段，域名使用保留示例域名。

```text
E1 09:00  VPN: account=A, session=V001, assigned_ip=10.10.2.15
E2 09:01  Endpoint: account=A, device=D001, logon_session=L001
E3 09:20  FileAudit: account=A, device=D001, project_file_reads=320
E4 09:40  Zeek: sensor=Z01, uid=C001,
          src=10.10.2.15, dest=203.0.113.8,
          direction=outbound, outgoing_ip_bytes=8589934592
E5 09:40  TLS metadata: sensor=Z01, uid=C001,
          server_name=upload.example.com（假定可观测）
```

通过有效时段内的 VPN 会话与设备登录，将网络行为关联到账号 A 与设备 D001，再由身份源将账号关联到人员 P001。E4 与 E5 通过同一传感器的连接标识关联；跨传感器不能未经验证就把 uid 当作全局唯一业务会话。

E3 与 E4 的时间接近仅建立调查线索。除非有文件上传、终端或代理等证据，不得声称 E4 传输的就是 E3 读取的文件。

### 3.2 特征与基线快照

```json
{
  "entity_id": "D001",
  "entity_type": "device",
  "feature_name": "daily_outgoing_ip_bytes",
  "feature_version": "example-v1",
  "window": "2026-09-10, Asia/Shanghai",
  "current_value": 8589934592,
  "unit": "IP bytes",
  "baseline_value": 858993459.2,
  "baseline_method": "illustrative threshold; not Splunk algorithm",
  "baseline_cutoff": "2026-09-10T00:00:00+08:00",
  "valid_history_days": 28,
  "identity_resolution": "VPN and endpoint corroborated",
  "evidence_ids": ["E1", "E2", "E4"]
}
```

当前值与基线之比为 10。此处使用“当日累计值已经超过完整可比日阈值”的示例口径；实际系统应明确日内时段或完整窗口比较规则，避免把半天与全天数据直接视为同一种分布。阈值、历史天数均是示意。

### 3.3 信号结构：让结果能被复算

```json
{
  "signal_id": "example-signal-001",
  "detector_id": "outgoing-volume-example",
  "detector_version": "v1",
  "entity_id": "D001",
  "related_person_id": "P001",
  "observed_at": "2026-09-10T09:40:00+08:00",
  "produced_at": "2026-09-10T09:50:00+08:00",
  "evidence_ids": ["E1", "E2", "E4", "E5"],
  "feature_snapshot_id": "example-feature-001",
  "base_score": 20,
  "risk_factor_version": "example-rf-v1",
  "calculated_score": 37.5,
  "explanation": "外发IP字节已达历史示例阈值10倍",
  "lineage": [],
  "status": "active"
}
```

上述结构参考了 Splunk 风险修饰关联实体、描述和威胁对象的思想，但字段由本报告构造。[13](https://help.splunk.com/en/splunk-enterprise-security-8/administer/8.5/risk-based-alerting/assign-risk-using-risk-modifiers-in-splunk-enterprise-security) 成熟实现还需定义证据访问权限、关系置信度、撤销或修订语义、幂等键及数据质量标记。

### 3.4 风险与案件不得再次制造事实

假定三条经确认独立的调整后贡献为 37.5、30、25，总和为 92.5。三个不同检测的最大分之和也为 92.5；最高单条分为 37.5，分数至少 50 的数量为零，发现数量为三。

这些数值可以用于演示 ERS 的五类输入，却仍然无法计算 Splunk 的最终 ERS，因为其具体权重和归一化未公开。[12](https://help.splunk.com/en/splunk-enterprise-security-8/administer/8.5/risk-based-alerting/entity-risk-scoring-in-splunk-enterprise-security) 案件可以引用这三条信号，不能把案件生成本身再当成第四份独立攻击证据。

## 4. 可以比较的实现组织方式

下表是工程取舍分析，未指定某个开源产品或技术栈，也不提供无实测依据的性能排名。

| 方式 | 主要计算方式 | 有利条件 | 成本或限制 |
|---|---|---|---|
| 搜索驱动 | 在事件存储上定时执行查询、摘要与检测 | 数据已集中，规则变化频繁，允许分钟级或更长延迟 | 周期扫描、摘要更新、搜索调度相互争用 |
| 持续计算 | 事件到达后更新窗口、身份和特征状态 | 对低延迟序列和持续增量有明确需求 | 迟到、状态恢复、升级迁移、回放复杂 |
| 混合方式 | 原文用于调查和回算，增量用于部分实时行为，批量建立历史基线 | 既要交互调查也要多时间尺度计算 | 两条路径的口径一致性和版本管理成本 |

Splunk 平台与本地 UEBA 可以提供搜索驱动思路，独立 UBA 提供流式加批量计算思路；它们只能证明不同组织方式均有应用实例，不能证明某一种必然适合我们的数据规模。[1](https://help.splunk.com/en/splunk-enterprise/administer/distributed-deployment-manual/9.1/overview-of-splunk-enterprise-distributed-deployments/components-and-the-data-pipeline)[9](https://help.splunk.com/en/splunk-enterprise-security-8/administer/8.7/user-and-entity-behavior-analytics/ueba-content-app-for-on-premises/roles-and-knowledge-objects-in-ueba-for-splunk-enterprise-security)[16](https://help.splunk.com/en/security-offerings/splunk-user-behavior-analytics/plan-and-scale/5.4.0/plan-and-scale-your-splunk-uba-deployment/splunk-uba-deployment-architecture)

### 4.1 是否复刻通用查询语言

实现完整类 SPL 平台会扩展到解析器、优化器、权限、分布式执行、知识对象和兼容性。若产品只支持限定防泄密场景，可使用受控检测定义；若分析师需要自由探索，则通用查询能力价值更高。该判断属于产品范围选择，不能仅由“Splunk 有 SPL”得出。

### 4.2 是否引入复杂模型

多维模型可能发现单一阈值遗漏的组合，也可能增加调试、样本需求和解释成本。个体统计能快速解释偏离，但会面对冷启动、小样本和角色变动。两者均需以真实业务误报样本和已知攻击样本验证，不以算法名称判定先进性。

### 4.3 是否把风险分作为主要入口

实体风险排序适合分析师主动调查，场景案件适合明确行动和闭环，直接告警适合确定性高危条件。可以并存，但必须避免同一行为在多入口被重复派发并重复计分。对用户呈现哪一种，应结合运营团队分工。

## 5. 机制验证矩阵

本次未执行这些实验。它们是后续验证清单，不是本报告声称已经通过的验收结果。

| 验证对象 | 实验方法 | 要观察的结果 | 它回答什么问题 |
|---|---|---|---|
| 字段语义 | 同一连接对比 Zeek 原文、TA 字段和 CIM 查询 | 地址、方向、字节、时间一致；缺失有标记 | 标准化是否改变业务含义 |
| 身份时效 | 两用户先后复用 IP，外加共享设备样本 | 历史事件仍归正确时段；冲突不会强制合并 | 用户评分是否可信 |
| 迟到事件 | 同批数据正常到达与延迟到达 | 正常、补算结果差异可解释；不重复加分 | 时间窗是否完整 |
| 重复回放 | 相同事件回放两次并重启计算进程 | 活跃信号与风险贡献不无故翻倍 | 系统是否具有业务幂等性 |
| 摘要延迟 | 人为制造摘要落后 | 诊断明确显示不完整；检测无告警不被当成正常 | 加速是否掩盖数据缺口 |
| 冷启动 | 新员工、新设备、短历史 | 显示未成熟或采用明确替代参照 | 是否会对新人集中误报 |
| 周期性业务 | 备份、发布、节假日、月末导出 | 异常原因与群体/时段解释符合实际 | 基线是否可比 |
| 单规则噪声 | 同一低质量行为连续触发上千次 | 观察实体排序、信号数量与案件量变化 | 抗噪能力是否真实存在 |
| 同源多规则 | 一条事件触发多个相似检测 | 可识别共同来源；不伪装成独立证据 | 多样性指标是否虚高 |
| 排除治理 | 对指定规则设置限时排除 | 模型查询、仪表盘、自定义查询口径一致或差异明确 | 调优是否可控 |
| 版本变更 | 改字节口径或特征定义后重算 | 历史与新状态有边界，可回滚和解释 | 升级是否造成伪异常 |
| 节点故障 | 任务中断、存储或状态节点重启 | 记录恢复时间、数据缺口、重复输出 | 高可用是否包含行为状态 |
| 可调查性 | 从案件回到原始记录 | 找到全部贡献证据、时间及版本 | 分析师是否能核实结论 |

对算法效果的评估至少同时报告：已审查告警的 precision、带标签场景的 recall、每千实体每日告警数、首次发现延迟分布及单案件调查耗时。真实生产中未被标注的攻击不能当作“没有漏报”，所以召回率必须声明测试集和攻击覆盖范围。

指标可采用：`precision=TP/(TP+FP)`，`recall=TP/(TP+FN)`。分母为零时结果不可计算。测试必须按时间划分训练与验证，避免未来数据进入历史基线；对同一攻击跨窗口的重复告警还需统一计数单位。

## 6. 后续取证应取得什么

| 需要的材料 | 用途 | 能解决的未知 |
|---|---|---|
| 固定版本的 ES、UEBA Content App 清单 | 对齐产品、版本、授权及部署模式 | 规则可编辑性与能力范围 |
| 对应保存搜索、宏、集合和模型定义 | 逐条追踪输入到输出 | 本地真实 SPL、特征结构、计算顺序 |
| 目标版本支持说明 | 明确管理员修改的支持边界 | 8.7 官方文档冲突 |
| 可控输入样本及运行任务信息 | 复现检测结果 | 窗口、延迟、摘要依赖和边界条件 |
| 风险数据模型及 ERS 运行观察 | 比较基础分、调整分、实体分 | 多因素、重复事件及排除的实际影响 |
| 本企业代表性正常与攻击样本 | 测量实用价值 | 误报、场景覆盖和运营负担 |

这些材料用于确认运行机制、依赖及支持边界；是否复用具体检测内容，是后续独立的产品决策。

## 7. 对原有资料的使用方式

原有清单可以继续用于寻找场景和关键词，但需要按第 05 分册的勘误解释。尤其要撤回以下外推：所有规则免训练、两代风险算法完整继承、本地可直接用云端测试索引、CIM 映射完成即等于内置检测已经支持、五组件保证不会刷分。

可交给领导判断的，是不同机制解决什么问题、依赖什么证据、付出什么代价，以及需要哪些实验才能决定。最终系统组织、模型复杂度、告警入口和建设范围不由本报告预先代选。
