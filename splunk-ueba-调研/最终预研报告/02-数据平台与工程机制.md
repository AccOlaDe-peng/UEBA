# Splunk 数据平台与工程机制

## 1. 从组件职责理解物理架构

【事实】Splunk 将输入、解析、索引和搜索分配给不同组件。Universal Forwarder 通常轻量采集转发；Heavy Forwarder 可以先解析再转发；Indexer 建立索引并参与搜索；Search Head 派发搜索并汇集结果。结构化输入等场景存在例外，不能绝对地说 Universal Forwarder 不解析任何数据。[1](https://help.splunk.com/en/splunk-enterprise/administer/distributed-deployment-manual/9.1/overview-of-splunk-enterprise-distributed-deployments/components-and-the-data-pipeline)

```text
日志文件 / Windows 事件 / API / HTTP 输入
                   │
                   ▼
       Forwarder 或输入端点
                   │
         可选 Heavy Forwarder
                   │
        ┌──────────┼──────────┐
        ▼          ▼          ▼
     Indexer A  Indexer B  Indexer C
     原文+索引   原文+索引   原文+索引
        ▲          ▲          ▲
        └──────────┼──────────┘
                   │ 搜索请求 / 结果
                   ▼
              Search Head
            SPL / 调度 / 展示
```

【解释】这张图表达责任边界，不规定节点数。小部署可以合并职责，大部署分离。将查询入口与存储计算分开，可以分别处理交互并发和数据规模；但是集中汇总仍然可能成为瓶颈。

### 1.1 管理平面与数据平面

Indexer cluster 的管理节点维护集群协调，Search Head Cluster 的 captain 协调集群活动和计划搜索。索引集群解决数据副本问题，搜索头集群解决搜索入口和任务协调问题，二者不能互相替代。[6](https://help.splunk.com/en/splunk-enterprise/administer/manage-indexers-and-indexer-clusters/10.4/how-indexer-clusters-work/search-factor)[24](https://help.splunk.com/en/splunk-enterprise/administer/distributed-search/9.0/overview-of-search-head-clustering/search-head-clustering-architecture)

【解释】自研时应明确哪些状态属于“原始数据”、哪些属于“控制配置”、哪些属于“运行中任务”。这些状态的恢复方法不同。增加 Kafka 副本并不自动保证模型状态或定时任务不会重复执行。

## 2. 接入与解析：哪些处理可以后补

### 2.1 最先确定事件边界和时间

【事实】索引前的处理包括事件切分、时间戳识别、默认元数据与特定索引时字段提取。搜索时可继续进行字段提取、别名、计算字段、查表、事件类型匹配和标签处理。[2](https://help.splunk.com/en/data-management/manage-splunk-enterprise-indexers/9.3/indexing-overview/index-time-versus-search-time)

【解释】假设一个 Java 堆栈应是一条事件，切成十条后会直接改变频次特征。假设日志是 UTC，解析成北京时间会使“夜间登录”发生系统性偏移。去掉敏感字段或入口丢弃事件之后，后续查询无法凭空还原它们。

| 数据项 | 在 UEBA 中的用途 | 常见故障 |
|---|---|---|
| 事件时间 `_time` | 行为顺序、时间窗、历史基线 | 时区错误、设备时钟漂移 |
| 索引时间 `_indextime` | 观察数据到达与积压 | 把迟到当作刚发生 |
| `host` | 事件来源上下文 | 把日志采集器当作行为设备 |
| `source` | 文件、流或输入来源 | 来源变化后重复采集 |
| `sourcetype` | 选择解析与语义规则 | 给不同格式错误使用同一解析器 |
| 原始事件 | 调查和重算依据 | 不可检索、保留期过短 |

这里的故障和 UEBA 用途属于工程分析。元数据的存在不自动保证对应业务含义正确。

### 2.2 接入成功与业务完整是两套验收

【解释】一条记录被接收，只能证明传输链路至少处理了这条记录。还必须对比源端产出量、事件类型分布、解析失败、迟到分布和关键字段覆盖率。身份审计少采集一个事件类型，可能恰好让“权限变更”整类检测失效。

HTTP/API 输入、文件转发和消息重试机制的确认语义并不相同。本次未逐协议验证端到端 exactly-once，因此不作“Splunk 保证全链路不丢不重”的结论。自研的信号层应另行定义幂等键、补采和重放策略。

## 3. 索引存储：为什么不必每次扫描全部原文

【事实】Splunk 将压缩原始数据、指向原始数据的 tsidx 文件和元数据组织成 bucket；bucket 具有时间范围。常规存储存在 hot、warm、cold 等生命周期，SmartStore 的远端存储场景不应简单套用同一冷热目录理解。[3](https://help.splunk.com/en/data-management/manage-splunk-enterprise-indexers/9.1/manage-index-storage/how-the-indexer-stores-indexes)

【解释】可以把一次查询理解为：先按时间和索引范围排除不相关 bucket，再利用索引定位候选事件，必要时读取原文并执行字段提取，最后计算结果。这是概念执行过程，不是对专有文件格式或每个优化器步骤的复现。

| 层次 | 保存什么 | 与 UEBA 的关系 |
|---|---|---|
| 原始事件 | 可回溯记录 | 说明信号从何而来；支持重新解析 |
| 基础索引 | 帮助查找事件的位置和字段/词项信息 | 减少查询候选范围 |
| 数据模型加速摘要 | 特定模型的字段化加速数据 | 多条检测复用相同标准化数据 |
| 行为特征或基线状态 | 按实体、时间、特征组织的派生值 | 减少反复处理长历史窗口 |
| 风险及案件数据 | 检测输出、聚合结果、处理状态 | 服务运营而不是替代原始日志 |

不能把 tsidx 直接称为 Elasticsearch 索引或某种通用列式数据库文件，也不能推断其未公开的编码、压缩算法和执行器实现。

### 3.1 保留周期为什么属于检测设计

【解释】原始日志保留 7 天，而模型比较 30 天历史时，必须有足够的历史派生状态；但有状态不等于能还原原始证据。若案件调查期长于日志保留期，后来可能只能看到“当时系统算出了什么”，看不到“事件究竟记录了什么”。

容量也不能仅按原始日志估计。摘要、副本、特征、模型、风险证据、检索缓存和回填临时空间都占用资源。每类数据都需要独立的保留、重建和恢复策略。

## 4. Schema-on-read 与 CIM：灵活性来自哪里

Schema-on-read 可理解为在读取和分析时解释部分字段。它不意味着完全没有 schema，也不意味着所有处理都发生在搜索时。Splunk 的索引时结构化提取与搜索时知识对象共同构成数据解释机制。[2](https://help.splunk.com/en/data-management/manage-splunk-enterprise-indexers/9.3/indexing-overview/index-time-versus-search-time)[L01](<../Splunk_TA_zeek/default/props.conf>)

### 4.1 一条日志经过哪些配置

| 对象 | 作用 | 可核对的配置位置 |
|---|---|---|
| 输入定义 | 指定采集对象及入口元数据 | `inputs.conf`，具体插件和部署决定 |
| 解析与属性 | 时间、结构化提取、别名、计算字段、查表调用 | `props.conf` |
| 转换与 lookup 定义 | 被解析或搜索配置调用的转换 | `transforms.conf` |
| 事件分类 | 用搜索条件定义事件集合 | `eventtypes.conf` |
| 标签 | 给事件类型附加语义标记 | `tags.conf` |
| 数据模型 | 定义对象约束、字段及派生计算 | `default/data/models/*.json` |
| 宏与保存搜索 | 复用表达式、组织检测与定时计算 | `macros.conf`、`savedsearches.conf` |

【解释】配置需要部署到执行对应阶段的组件。索引前规则只装在 Search Head，不会使远端 Indexer 对过去事件重新切分；搜索字段配置没有进入有效作用域，也不会因为原文里出现了相似字符串就自动生效。

### 4.2 本地 Zeek 插件中的实际证据

本地 `Splunk_TA_zeek/default/app.conf` 声明的是 **Corelight Add-on for Zeek 1.0.11**。不能将其与相邻 `Splunk_TA_bro` 目录或不同版本压缩包视为同一插件。[L05](<../Splunk_TA_zeek/default/app.conf>)

以下片段摘自本地 `props.conf`，保留了实际字段选择：[L01](<../Splunk_TA_zeek/default/props.conf>)

```ini
[zeek]
INDEXED_EXTRACTIONS = tsv
KV_MODE = none
TIMESTAMP_FIELDS = ts

[zeek:conn]
FIELDALIAS-id_orig_h = id_orig_h ASNEW src id_orig_h ASNEW id.orig_h id_orig_h ASNEW src_ip
FIELDALIAS-id_resp_h = id_resp_h ASNEW dest id_resp_h ASNEW id.resp_h id_resp_h ASNEW dest_ip
FIELDALIAS-orig_bytes = orig_ip_bytes ASNEW bytes_out
FIELDALIAS-resp_bytes = resp_ip_bytes ASNEW bytes_in
```

需要看配置右侧的源字段，不能根据 stanza 名 `FIELDALIAS-orig_bytes` 就以为映射来自 `orig_bytes`。实际使用 `orig_ip_bytes`，与应用有效载荷字节不是相同口径。Zeek 官方字段定义区分这两个量。[25](https://docs.zeek.org/en/current/scripts/base/protocols/conn/main.zeek.html)

本地插件还用 `local_orig`、`local_resp` 派生 direction，无法判定时设置 unknown。若采集数据没有匹配这些条件所需的值，“外发流量”过滤就可能漏掉事件；真实输入中的布尔值解析也需要验证。[L01](<../Splunk_TA_zeek/default/props.conf>)

事件分类链路为：[L02](<../Splunk_TA_zeek/default/eventtypes.conf>)[L03](<../Splunk_TA_zeek/default/tags.conf>)[L04](<../Splunk_SA_CIM/default/data/models/Network_Traffic.json>)

```text
sourcetype=zeek:conn
    → eventtype=zeek_network_traffic
    → tags: network, communicate
    → 满足 CIM Network_Traffic 相应对象的约束
    → 使用 src、dest、bytes_out 等字段进行分析
```

【解释】这里证明了映射方式，尚未证明目标环境的实际日志能正确命中全部约束，也未证明 ES 内置本地 UEBA 正式支持任意 Zeek 数据替代已验证数据源。应实测字段、模型对象覆盖和内容依赖。

### 4.3 CIM 的实际价值与边界

本地 CIM 8.7.0 提供 Network_Traffic、Authentication、Endpoint 等模型定义。ES 8.6 本地 UEBA 所需数据源页面列出 Authentication、Network_Traffic、Web、Change、Endpoint、Email 六类模型及对应已验证来源。[L04](<../Splunk_SA_CIM/default/data/models/Network_Traffic.json>)[L06](<../Splunk_SA_CIM/default/app.conf>)[11](https://help.splunk.com/en/splunk-enterprise-security-8/administer/8.6/user-and-entity-behavior-analytics/ueba-detections-in-splunk-enterprise-security/required-sourcetypes-for-ueba-detections)

【解释】标准化使规则可以面向“认证行为”而非某个厂商的原始格式，但不负责创造缺失信息。网络连接日志没有用户身份，字段别名不会产生可信用户；TLS 元数据没有文件内容，映射到 Web 或网络模型也不会得到敏感文档名称。

## 5. SPL 如何执行，为什么查询写法影响成本

SPL 采用管道表达处理步骤：筛选事件、提取字段、计算、聚合和输出。命令的执行属性决定工作能够在 Indexer 分散完成，还是需要把数据汇集到 Search Head。可分布式 streaming 与集中式 streaming 是不同类别；“streaming 命令”也不等于持续消费消息的独立实时系统。[4](https://help.splunk.com/en/splunk-cloud-platform/search/search-manual/10.2.2510/search-overview/types-of-commands)

【示例】以下查询仅用于解释执行结构，未在 Splunk 上运行；假设索引、插件和字段都已经配置正确：

```spl
index=network sourcetype=zeek:conn earliest=-65m latest=-5m
| where direction="outbound" AND isnotnull(src) AND isnotnull(bytes_out)
| stats sum(bytes_out) AS outgoing_ip_bytes count AS connections BY src
| sort - outgoing_ip_bytes
```

从语义看，它计算一个固定历史窗口内各源地址的外发 IP 字节量。它不包含身份解析、个人基线或异常判定，也不能被称为完整的外泄检测。

【解释】越早限制索引、时间和候选集合，越容易减少后续处理量。全局排序、高基数聚合、复杂关联和大规模字段提取都可能增加内存或汇集开销。不能简单认为“加几台 Indexer，所有 SPL 就线性变快”；实际执行计划还需 Job Inspector 等运行证据确认。

### 5.1 普通查询、摘要和数据模型加速

【事实】Data Model Acceleration 为数据模型的字段建立额外 tsidx 摘要。它加速一组模型字段上的分析，与针对单条报表的预计算不同。`tstats summariesonly=true` 只读取已摘要部分，不返回未摘要数据。[5](https://help.splunk.com/en/splunk-enterprise/manage-knowledge-objects/knowledge-management-manual/10.0/use-data-summaries-to-accelerate-searches/accelerate-data-models)

【示例】

```spl
| tstats summariesonly=true sum(All_Traffic.bytes_out) AS outgoing_ip_bytes
  FROM datamodel=Network_Traffic.All_Traffic
  WHERE earliest=-65m latest=-5m All_Traffic.direction="outbound"
  BY All_Traffic.src
```

这段示意假设数据模型已加速、字段有效且摘要覆盖了时间范围。它与上面的原始索引查询可能并非完全相同的数据集合，尤其当模型还纳入了其他来源时。验证时必须先统一范围。

【解释】摘要会把字段解释的计算成本提前付出，但也形成新鲜度问题。若摘要落后 20 分钟，使用 `summariesonly=true` 的查询可能很快返回少量数据，而不是显式报错。对安全检测来说，结果少不一定意味着行为少。

## 6. 搜索怎样成为持续运行的检测

【事实】本地 UEBA 的保存搜索不只有最后一条检测，还包含 summarization、consolidation、feature 和 scoring；宏与 KV Store 一起参与运行。[9](https://help.splunk.com/en/splunk-enterprise-security-8/administer/8.7/user-and-entity-behavior-analytics/ueba-content-app-for-on-premises/roles-and-knowledge-objects-in-ueba-for-splunk-enterprise-security)

【解释】其工程本质是具有依赖关系的派生数据流水线。可以用下面的依赖示意理解，而不能把示意中的具体顺序或周期当成厂商所有规则的实现：

```text
可分析事件
   → 小窗口摘要
   → 按实体合并历史
   → 特征 / 历史状态
   → 当前行为评分
   → 输出信号
```

### 6.1 三种时间必须分清

| 时间 | 例子 | 决定什么 |
|---|---|---|
| 数据事件时间 | 09:40 发生传输 | 行为所属窗口 |
| 任务执行时间 | 09:50 运行检测 | 系统何时处理 |
| 基线截止时间 | 使用 00:00 前已完成历史 | 比较参考是否泄漏当前信息 |

【示例】每 5 分钟运行一次，读取 `[now-10m, now-5m)`，是在为到达延迟留缓冲。这种调度仍需补采处理：晚到 30 分钟的数据会错过正常窗口。若扩大查询窗口，又可能重复产出信号。

可以给自研信号定义 `hash(检测版本, 实体ID, 窗口起点, 证据集合标识)` 作为幂等键。回放时先更新已有信号而非再次加分。这是自研设计示意，不是 Splunk 已公开的幂等算法。

### 6.2 状态错位比单次失败更难发现

【解释】特征搜索使用今天的数据，而 scoring 搜索读到前天的基线，作业可能全部“成功”却给出错误结果。因此流水线健康不能只有成功/失败，还需要数据覆盖截止点、基线版本、输入分区及最后更新时刻。

修改字段映射后，也可能同时存在旧口径摘要、新口径原始搜索和旧基线。若没有变更边界，系统会把口径变化误判成行为变化。数据模型、特征与检测版本需要一起审计。

## 7. 高可用和扩展：副本解决什么

【事实】索引集群按 bucket 复制。Replication Factor 描述数据副本数量，Search Factor 描述可搜索副本数量，后者不能大于前者。可搜索副本包含用于查询的索引文件；只有原始数据的副本与可立即搜索的副本并不等价。[6](https://help.splunk.com/en/splunk-enterprise/administer/manage-indexers-and-indexer-clusters/10.4/how-indexer-clusters-work/search-factor)

【解释】容量规划要同时考虑正常查询与故障期间恢复。集群节点故障后补副本、重建索引或恢复摘要，都会与业务计算争用资源。副本也不是长期备份：错误配置、错误删除或污染状态可能影响多个副本。

### 7.1 一个仅用于量级沟通的容量例子

【示例】假定 20,000 EPS、每事件平均 800 字节，则原始输入为：

```text
每日事件数 = 20,000 × 86,400 = 1,728,000,000
每日字节数 = 1,728,000,000 × 800 = 1,382,400,000,000
           ≈ 1.3824 TB / 日（十进制）
30 日原始输入 ≈ 41.472 TB
```

这不是磁盘需求，也不是 Splunk 官方性能数据。磁盘估计还需要实测压缩、索引、摘要及副本开销。CPU 和内存取决于字段提取、并发查询、实体与分组基数、模型和回算强度，不能从 EPS 单独推算。

行为状态还有另一种规模：`实体数 × 特征数 × 时间分桶数`。例如 10 万实体、40 个特征、30 个每日槽位就是 1.2 亿个特征槽位，尚未包含稀有值集合及多对多关系。不能因原始数据存储充裕就认为 KV 或特征层不会成为瓶颈。

## 8. 权限、变更与可观测性

【事实】ES UEBA 区分管理员、分析师及普通用户的知识对象访问；8.7 文档尤其限制特征、关联身份和资产集合的访问。[9](https://help.splunk.com/en/splunk-enterprise-security-8/administer/8.7/user-and-entity-behavior-analytics/ueba-content-app-for-on-premises/roles-and-knowledge-objects-in-ueba-for-splunk-enterprise-security)

【解释】画像本身比单条日志更容易暴露人员行为模式。自研权限需要作用于数据、模型状态、检测编辑、例外规则和案件，不能只限制仪表盘菜单。计划任务以何种身份访问哪些数据，也会改变检测覆盖。

应分别监控接入、解析、模型覆盖、特征更新、检测调度、信号产出、风险刷新和调查回查。对“没有告警”至少区分：正常无异常、没有输入、字段缺失、模型未成熟、任务未运行、摘要落后、权限不足、被排除。Splunk 的 UEBA 审计页提供了这种诊断方向，但具体自研指标仍需设计。[10](https://help.splunk.com/en/splunk-enterprise-security-8/administer/8.6/user-and-entity-behavior-analytics/auditing-ueba-with-dashboards-in-splunk-enterprise-security)

## 9. 平台机制对自研的含义

能借鉴的是“保留事实、统一语义、复用计算、按实体组织状态、解释结果”的机制。是否实现通用 SPL、是否采用搜索引擎、是否引入流处理及独立特征存储，应由具体场景和测量结果决定。

本次证据不足以复现 Splunk 的 tsidx 二进制格式、完整查询优化器、云服务内部拓扑、全链路投递一致性及所有调度实现。它们是待单独验证的边界，不应在自研预算中被当作已经解决的问题。
