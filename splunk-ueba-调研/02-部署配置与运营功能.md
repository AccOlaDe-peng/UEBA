## 1. 部署架构与前置条件

### 1.1 UEBA 相关应用(App)构成

ES 8.5 Premier Edition 中有两个 UEBA 相关应用:

| 应用 | 名称 | 分发方式 | 作用 |
|---|---|---|---|
| DA-ESS-UEBA | UEBA App | ES Premier 默认内置(云 + 本地) | 提供 UEBA 仪表盘与基础能力,**无需单独安装** |
| DA-ESS-UEBAContent | UEBA Content App | 仅本地(on-premises)部署可从 Splunkbase 下载 | **扩展 UEBA 功能、解锁更多 UEBA detections** |

**UEBA Content App 安装要点:**
- 从 Splunkbase 用 Splunk.com ID 登录下载(必须是 licensed user)。
- **必须安装在与 Splunk Enterprise Security 相同的 search head 上**,以 administrator 登录,通过 `Apps > Manage Apps > Install App from File` 上传安装。
- Search Head Cluster(SHC)环境:按「Install Splunk Enterprise Security in a search head cluster environment」文档部署。
- 索引集群(indexer cluster)环境:需按文档配置并部署 **`ueba_summaries` 索引**(UEBA 摘要数据存放处)。

### 1.2 UEBA 工作原理(官方概述)

UEBA 通过将当前活动与**学习到的基线(baseline)**对比来识别异常,用于发现内部威胁、减少误报、按风险排定调查优先级。流程:

1. 从多源(认证日志、终端、网络流量等)**采集并关联行为特征**(如登录频次、数据访问量);
2. 为每个用户/实体**建立正常活动基线**;
3. **度量对基线的偏离**;
4. 偏离显著时生成 **intermediate findings(中间发现)**;
5. findings 汇入 **Entity Risk Score(ERS,实体风险分)**,指示潜在威胁。

**检测特点**:UEBA detections 不依赖固定规则,而是使用统计模型/机器学习判断"对该用户或资产而言何为正常"。**官方不允许用户修改 UEBA 检测的底层 SPL 与逻辑**,只能通过 finding exclusions 调优其产出。

### 1.3 使用 UEBA 的前置条件清单

| 前置任务 | 对应文档 |
|---|---|
| 验证兼容性 | UEBA compatibility |
| 给需要 UEBA 访问的用户授权 | Roles and knowledge objects in UEBA |
| 在 Asset and Identity Framework 中采集并提取数据 | Configure asset and identity data for UEBA |
| 配置 risk-based alerting(RBA) | Risk scoring in Splunk Enterprise Security |
| 验证 UEBA 所需 sourcetypes | Required sourcetypes for UEBA detections |

**访问入口**:ES 菜单 `Analytics > UEBA`。

### 1.4 服务限制(Service Limits)

**本地部署(on-premises):**
- Entity lists:共 **500** 个(identity + asset,含 source/category/pattern match 各类型);
- Finding exclusions:共 **2,000** 条(含 field match 与 lookup 各类型)。

**云部署(UEBA Cloud,per tenant):**
| 限制项 | 数值 |
|---|---|
| 事件吞吐(EPS) | 45,000–60,000 EPS |
| 唯一用户数 | 最多 3,000,000 |
| 唯一设备数 | 最多 3,000,000 |
| Entity lists | 500 |
| Finding exclusions | 2,000 |

> 设计参考:官方明确说明设置服务限制的目的——保证性能可预期、防止过载、支持扩展、满足合规、控制成本。

## 2. 角色与权限/知识对象

UEBA **复用 Splunk 平台/ES 的既有用户与角色体系**,不新增独立角色。可用默认角色:`admin`、`sc_admin`、`ess_admin`、`ess_analyst`、`ess_user`。

### 2.1 UEBA 知识对象(Knowledge Objects)权限矩阵

| 知识对象 | 在 UEBA 中的用途 | 读权限 | 写权限 |
|---|---|---|---|
| Saved searches | UEBA 检测规则及其配套的 summarization / consolidation / feature / scoring 搜索 | 所有角色 | admin, sc_admin, ess_admin |
| KV Store collections | 追踪特征值(feature values)、相关身份、相关资产 | admin, sc_admin, ess_admin | admin, sc_admin, ess_admin |
| Search macros | 封装数据映射、字段值转换、特征计算、事件打分 | admin/sc_admin/ess_admin/ess_analyst/ess_user | admin, sc_admin, ess_admin |
| Transforms | 让 collections 可被 SPL 使用 | 所有角色 | admin, sc_admin |
| Views | 提供 UEBA 仪表盘访问 | admin/sc_admin/ess_admin/ess_analyst/ess_user | admin, sc_admin, ess_admin |

### 2.2 各角色的 UEBA 能力

| 角色 | UEBA 能力 |
|---|---|
| ess_admin | 配置/修改/管理全部 UEBA 内容;编辑搜索、collections、macros、仪表盘;查看追踪用户/设备/特征值的 lookups |
| ess_analyst | 查看与使用 UEBA 仪表盘;在搜索中执行 macros;查看 saved searches;**不能修改配置,不能查看追踪类 lookups** |
| ess_user | 同 ess_analyst(纯只读使用) |

### 2.3 权限故障排查

| 现象 | 解决办法 |
|---|---|
| 无法查看 UEBA System 仪表盘 | 继承 ess_admin / ess_analyst / ess_user 之一 |
| 搜索中 macros 不可用 | 同上 |
| 无法修改 UEBA detections | 继承 admin / sc_admin / ess_admin 之一 |
| collections 不可访问 | 同上 |

> 设计参考:三档分层(管理/分析/普通用户)+ 按知识对象类型(搜索、KV Store、宏、transforms、视图)分别授权,是可复用的权限模型。KV Store 存特征值(用户行为画像数据)且只对管理员可见,体现了"行为基线数据属敏感数据"的设计考量。

## 4. 资产与身份数据要求

UEBA 使用 ES 的 **Asset and Identity Framework** 完成:
- 将 intermediate findings **关联到正确的用户或资产**;
- 用该用户/资产的属性**丰富(enrich)findings**;
- 资产身份数据**驱动 entity lists**、为 findings 提供上下文、**保证风险分数算给正确的实体**;
- 支持 peer grouping(同侪分组)与 risk object 归一化。

**配置要求:**
1. Asset and Identity Framework 已搭建且填充了准确数据(可从内部数据源采集,或通过 Splunk Supporting Add-on for Active Directory 之类集成);
2. 在 Asset and Identity Management 页面**至少配置并启用一个 identity source**。

**UEBA 依赖的字段(用于归一化 risk object、同侪分组、上下文展示):**

Identity(身份)字段:
`first` `last` `Email` `identity` `managedBy` `bunit` `StartDate` `EndDate` `Category`

Asset(资产)字段:
`asset` `asset_tag` `bunit` `category` `city` `country` `dns` `ip` `Mac` `nt_host` `owner` `pci_domain` `priority`

若资产/身份数据缺失,UEBA diagnostics 仪表盘会显示相应错误(见第 9 节)。

> 设计参考:ES 用统一框架字段清单约束资产/身份数据模型,UEBA 明确声明"我依赖哪些字段、用于什么"。自研产品可借鉴:定义实体 schema 的最小必需字段集,并给数据质量做诊断面板。

## 5. Finding Exclusions(发现排除规则)

### 5.1 解决什么问题

用于**从 Risk Data Model 中移除不需要的 intermediate findings**,降噪并提高 UEBA 检测准确性。典型场景:
- 压制由合法或低风险行为触发的 findings;
- 减少周期性模式/流程豁免导致的误报;
- 让 UEBA 仪表盘与风险模型聚焦于有意义的异常;
- 避免实体风险分数虚高、缓解 alert fatigue。

### 5.2 生效逻辑(关键设计)

- 排除的 findings 不会进入:**UEBA 仪表盘与实体风险评分(ERS)**、**使用 risk data 的检测**、**risk-based alerting 与 MITRE ATT&CK 映射**。
- **每条规则绑定且仅绑定一个检测(detection-specific)**,创建后**不能更换关联的检测**(只能另建规则)。
- 规则可设置**结束日期**或选择 **No end date(无限期)**;到期自动失效。
- 每条 active 规则**名称必须唯一**。
- 创建后可通过 Rule status 开关启用/停用;**最多同时开启 2,000 条 field match 规则**。
- **生效延迟**:新规则最长 30 分钟生效,或手动点 **ERS Refresh** 立即触发;lookup 类规则的值复制到 indexer 最多延迟 10 分钟。
- 提供 **Preview excluded findings**:在新的搜索页预览该规则将排除哪些 intermediate findings(先看后开)。
- 入口:`Configure > Findings and investigations > Finding exclusion rules`(管理页),或 `Configure > UEBA > Finding exclusion rules` 标签页。

### 5.3 创建方式一:从资产/用户分析上下文创建

1. `Analytics > UEBA`;
2. 在 **Top risky users / Top risky assets** 中选择用户或资产,进入分析仪表盘;
3. 在 **Detection activity** 面板,点某检测旁的配置图标,打开 "Add finding exclusion rule" 对话框;
4. 填 Name、选 Reason(Remediated / Accepted / Detection accuracy 三选一);
5. Conditions 里填 End date 或勾 No end date;
6. 填 **Field + Matching criteria** 对(字段取自 intermediate finding,如 `normalized_risk_object` = `*_`);一个 lookup 字段只能映射一个 finding 字段;多对条件之间是 **AND**;
7. (可选)Preview excluded findings;
8. Add。

### 5.4 创建方式二:从 UEBA 配置页创建(三种条件类型)

1. `Configure > UEBA > Finding exclusion rules 标签 > Add rule`;
2. 条件类型三选一:
   - **Entity list**:下拉选择已建好的实体清单(可复用已有实体定义,跨关键用户/实体一致地套用排除);
   - **Lookup**:选 lookup 文件,配 Lookup field ↔ Finding(intermediate finding)field 对(如 `workstation` ↔ `normalized_risk_object`);同一 lookup 字段可配多条匹配条件,相互之间是 **OR**;
   - **Field match**:直接填 Field + Matching criteria 对;
3. 其余(Name/Reason/End date/AND/Preview)同方式一。

### 5.5 编辑与审计字段

编辑:`Configure > UEBA > Finding exclusion rules` 表格中点编辑图标,改完 Save。管理列表含配置值与审计字段(创建/更新信息),并显示当前匹配状态。

> 设计参考:三档 Reason(Remediated 已修复 / Accepted 风险接受 / Detection accuracy 检测准确性)是很好的"排除原因治理"设计;规则绑定单一检测 + 生效延迟 + 预览 + 数量上限 + 到期机制,共同构成排除规则的生命周期管控,避免排除被滥用导致检测失效。

## 6. UEBA 仪表盘全景 ★

数据来源:Risk data model 中的 detections 与 findings(`index=risk`)。进入方式:`Analytics > UEBA`,在搜索栏输入用户或资产名。注意:风险计算与 lookups **最多需 30 分钟**才显示;若 1 小时后仍为空,先查 `index=risk` 中有无 findings。

### 6.1 官方仪表盘列表(UEBA app 内)

| 仪表盘 | 用途 |
|---|---|
| **UEBA overview** | 展示环境高层行为指标与整体实体风险;用于识别最近活动最多或行为最异常的实体。支持按 **Entity list** 下拉过滤(可多选;另有 `Uncategorized` 选项,筛选不属于任何清单的实体) |
| **Entity analysis**(User analysis / Asset analysis 两种形态) | 特定用户(或资产:服务器/终端/设备)的详细行为与上下文:风险分、关联、检测、调查 |
| **Entity risk score** | 实体**当前与历史**风险分,并按**贡献因子(factor)**与 **MITRE ATT&CK tactic** 细分 |
| **Entity detection activity** | 列出所选实体命中的 detections、findings 及其分数;可查看风险详情、finding exclusions、UEBA baselines |
| **All related investigations** | 展示 Mission Control 中与所选用户/资产关联的调查 |

(`view-ueba-dashboards` 页面同时使用了 UEBA Overview / User Analysis / Asset Analysis 的叫法,即 overview + 按实体类型的分析视图。)

### 6.2 Entity Analysis 仪表盘的关键面板(自研可重点参考)

| 面板 | 内容 |
|---|---|
| Entity risk score | 过去 7 天的风险分 + 趋势 sparkline;点 "Show calculation" 查看分数构成与 ATT&CK 映射(**分数可解释性**) |
| Entity details | 用 Assets & Identities 表 enrich 的组织归属信息;同时显示 **Entity lists 字段**(该实体属于哪些清单) |
| Connection panels | 基于近期活动的相关用户/资产关系("Show related users and connections" 展开更多关系) |
| Detection heat map | 每个检测的 findings 数量热力图,hover 看上下文 |
| Entity detection activity | 检测列表:finding 计数、分数贡献、first/last seen;Actions 图标可查看 risk details / 打开 finding exclusions / 展示 **UEBA baselines** |
| Contributing risk | 对总分有贡献的 findings / intermediate findings 明细 |
| Finding exclusions | 从实体上下文直接发起排除(见 5.3) |
| UEBA baseline visualizations | 交互式展示 UEBA 模型基线与异常(**"为什么异常"的可视化**) |
| All related investigations | 该用户/资产当前与历史的调查(Mission Control) |
| Look-back period | 调整面板时间范围(如最近 7 天 / 30 天) |

## 7. Entity Lists(实体清单)

### 7.1 概念与用途

Entity List 定义一组实体(用户、主机、设备),用于在仪表盘与检测中 **include / exclude**:
- 让仪表盘聚焦于关注的实体;
- 排除已知安全/低优先级的实体;
- 复用 curated 名单做持续监控或对比。

应用后,entity lists 会更新 UEBA 仪表盘的包含/排除范围,帮助更快调查、更清晰的行为洞察、更高效的分诊。**还可以作为 finding exclusion rule 的条件来源**(见 5.4),实现更精准的检测调优。

### 7.2 创建(Add a new entity list)

1. `Configure > UEBA > Entity lists 标签 > Add entity list`;
2. 选择清单对象类型:**Assets** 或 **Identities**;
3. 命名:**3–100 字符、唯一、不能用 "uncategorized"**(该名保留给"不属于任何清单"的过滤项);
4. 选择清单条件(List condition),三种方式:
   - **Source**:从资产/身份 lookup 中已有的 source 选择;
   - **Category**:从资产/身份 lookup 中已有的 category 选择;
   - **Pattern match**:输入对 `normalized_risk_object` 值做匹配的模式;
5. (可选)Preview 区点 **Run**,保存前预览有多少实体满足条件(基于资产/身份 lookup 中的实体);
6. Add。

### 7.3 管理与管理信息

`Configure > UEBA > Entity lists`:列表展示每条清单的配置值、**审计字段**、**当前匹配实体数量**。可编辑(铅笔图标,但**不能改清单名**);可删除(垃圾桶图标,**删除清单不影响底层 Assets & Identities Framework 数据**)。总量上限 500(见 1.4)。

### 7.4 查看某实体属于哪些清单

`Analytics > UEBA` → 打开实体分析页 → **Entity details 面板 → Entity lists 字段**;若属于多个清单,hover "+" 图标可见其余清单。

> 设计参考:entity list 是"静态组织知识"(资产分组、身份分组)注入行为分析通道的接口——既服务可视化过滤,也服务检测排除,一处定义、多处复用;动态预览匹配数量 + 保留 Uncategorized,是很实用的交互细节。

## 8. 调查工作流(把用户/资产加入 investigation)

前提:该用户/资产相关数据已在 Risk Data Model 中(即第 4 节的资产身份数据已就绪)。

流程(在 User analysis / Asset analysis 页面内完成,不离开分析工作流):
1. `Analytics > UEBA`;
2. 从表中选择用户/资产,打开 UEBA 实体分析仪表盘;
3. 点 **Start investigation** 打开调查对话框(若该实体已有活动调查,也可点 more 图标再选 Start investigation);
4. 二选一:
   - **创建新调查**:输入调查名称 + 可选描述;
   - **加入现有调查**:从列表选择;
5. 点 Start investigation 完成。

> 设计参考:"从风险视图一键转调查"打通了检测(ERS/仪表盘)到响应(Mission Control 调查)的闭环,自研产品应有等价的 entity → case 工作流。

## 9. 审计能力(Auditing UEBA)

官方提供两个审计视图:

### 9.1 UEBA Diagnostics 仪表盘

入口:`Analytics > Audit > Entity risk score diagnostics`。用于:
- 确认实体与资产数据被正确摄取;
- 检查 MITRE ATT&CK 映射与注解是否符合预期;
- 排查风险分数缺失/异常、面板为空等问题。

两个 Tab:
- **Operational health**:关键 UEBA 组件的健康状态(pass/fail);
- **Entity risk score (ERS)**:实体评分过程可见性,确认风险数据被正确评估。

**MITRE ATT&CK 审计搜索**(官方给出,用于检查检测是否带 ATT&CK 注解):
```spl
index=risk
| fields - annotations*
| dedup source
| lookup correlationsearches_lookup _key AS source OUTPUTNEW annotations
| lookup ba_detections_lookup _key AS source OUTPUTNEW annotations
| eval annotations = mvindex(annotations, 0)
| eval mitre_id=coalesce(json_array_to_mv(json_extract(annotations, "mitre_attack")), "null")
| table source, mitre_id
```
`mitre_id` 为 null 的可能原因:检测无 ATT&CK 注解;注解数据未进入 `correlationsearches_lookup` 或 `ba_detections_lookup`;缺少 risk 索引访问权限;检测未开启或未产生 findings。

### 9.2 UEBA System 仪表盘(仅本地部署)

- 作用:为本地 Premier 版的 **Rare Device\*** 与 **Unusual Volume\*** 两族检测提供运行可视性;展示**过去 24 小时**内被追踪用户/设备的分数快照;用途是**确认检测已激活且在处理数据**(即使尚未生成 intermediate finding)。
- 入口特殊:**不在标准导航菜单中**,需直接访问 URL:`(instance)/en-US/app/SplunkEnterpriseSecuritySuite/ueba_system`。
- **Rare Device Feature Scores (Yesterday)** 面板解读:
  - 每行代表一次具体登录活动(同一用户+设备的多次登录会有多行,属正常);
  - 模型对各 feature 打分,**分数越低越稀有**;
  - **稀有阈值:小于 0.002 视为 rare,表中红色高亮**;
  - `behavior_rarity` 分数 = 该事件中稀有 feature 的数量;**高分不保证生成 intermediate finding**(系统有额外的减误报逻辑)。
- **Unusual Volume of \*** 面板解读:每行是一个用户 + 被追踪 feature;展示特征计算值与**个体基线阈值(individual baseline)**,超过阈值即视为潜在风险。

> 设计参考:审计层覆盖"管道健康(Operational health)、评分正确性(ERS)、ATT&CK 注解完整性、单检测运行可视性(System dashboard)"四个维度;把模型内部指标(feature 分数、个体基线阈值、稀有阈值)直接暴露给运营者,便于验证"检测为什么(没)告警"。

## 10. Behavioral Analytics Service(行为分析服务)

### 10.1 定位

- Behavioral Analytics Service(BA service)是 **Splunk 云侧提供的基于行为的检测服务**,其检测以 **"Behavior-based detection" 类型、"Behavioral analytics service" 应用**的形式出现在 ES 的 Content Management 中;主要面向 **Splunk Cloud 平台**客户。
- 与本地 UEBA Content App 是互补关系:本地装 DA-ESS-UEBAContent 获得(更多)UEBA detections;云上由 BA service 投递 behavior-based detections。
- 服务使用**数据源生成 anomalies(异常)**,再由检测消费。
- 检测产生的事件默认写入 **test index `ba_test`**(见 10.4), opt-in 后才进 risk index。

### 10.2 支持的数据源 ★

- **唯一列出的通用转发器数据源:Windows 安全日志,sourcetype `XmlWinEventLog:Security`**(经 universal forwarder 采集)。
- **BA 服务支持的 Windows Event ID(共 22 个)**:

| Event ID | 说明 |
|---|---|
| 4103 | Windows 许可证激活失败 |
| 4104 | PowerShell 脚本块日志(Script Block Logging) |
| 4624 | 账户成功登录 |
| 4625 | 账户登录失败 |
| 4648 | 使用显式凭据的登录尝试 |
| 4661 | 请求对象句柄 |
| 4662 | 对对象执行了操作 |
| 4663 | 尝试访问对象 |
| 4670 | 对象权限被更改 |
| 4673 | 调用了特权服务 |
| 4688 | 新进程已创建 |
| 4689 | 进程已退出 |
| 4720 | 用户账户被创建 |
| 4723 | 尝试更改账户密码 |
| 4726 | 用户账户被删除 |
| 4756 | 成员被添加到安全组 |
| 4757 | 成员被从安全组移除 |
| 4768 | 请求 Kerberos 认证票证(TGT) |

> 能力域画像(按事件 ID 归类):进程创建/退出(4688/4689)、PowerShell 执行(4103/4104)、登录与凭据(4624/4625/4648/4776)、Kerberos(4768/4769/4771)、账户与组管理(4720/4723/4726/4756/4757)、对象访问与权限(4661/4662/4663/4670/4673)。即 BA 服务当前聚焦 **Windows 端点行为**。

### 10.3 支持的检测 ★

- **ES 8.5 官方文档不再内联列出检测清单**,该页面仅一句话:"完整清单见 Splunk Security Content 网站(research.splunk.com)"。
- **完整枚举清单没有公开渠道可得**(2026-09-09 复查结论):
  - 8.5 文档页只链接到 `https://research.splunk.com/` 根路径;8.0/8.1/8.2 版页面已 404,8.3 版同样只指向 research.splunk.com;Wayback Machine 无该页快照。
  - research.splunk.com 站点 sitemap 共 4,855 个 URL,全部是 ESCU(Splunk Security Content)公开检测/基线/攻击数据,**没有任何 behavioral analytics service 条目**(全站无 "behavioral" 命名);其检测页统一标注 `Product: Splunk Enterprise Security`。
  - GitHub `splunk/security_content` 仓库(4,313 个文件)中 26 个文件名含 "behavior",但均为 ESCU 的 RBA "risk behavior" 类检测(如 `o365_email_suspicious_behavior_alert`、`windows_common_abused_cmd_shell_risk_behavior`),不是 BA 服务检测。
  - 结论:BA 服务的检测属于 **Splunk Cloud 侧闭源内容**,官方从未公开完整枚举;"Security Content 网站"那句指引是泛指,不是一个可过滤出 BA 检测的清单页。
- **实际可行的盘点途径**(需产品环境):
  1. ES 中 `Security content > Content management`,用 **Type = Behavior-based detection** 与 **App = Behavioral analytics service** 过滤,即得该租户可用的完整清单;
  2. 开启 ba_test 沙箱后按 `index=ba_test` 按检测 `source` 字段盘点实际触发的检测;
  3. 每条检测详情页可见:版本、日期、关联 analytic story、触发所需数据、**安全框架映射(MITRE Technique、Cyber Kill Chain、CIS20、NIST)**、以及检测使用的 SPL。
- **输入面即能力面**:BA 检测只消费 10.2 的 22 个 Windows 安全事件 ID(进程 4688/4689、PowerShell 4103/4104、登录 4624/4625/4648/4776、Kerberos 4768/4769/4771、账户管理 4720/4723/4726/4756/4757、对象访问 4661/4662/4663/4670/4673),所有异常模型均围绕这些事件构建。
- **最接近的公开替代物**(做自研参考时可用):
  - UEBA 云端检测参考清单 176 条 / 本地 119 条(见分册 01,文档页 `ueba-detection-reference-for-ueba-cloud` / `-on-premises`);
  - research.splunk.com 上按 Anomaly 类型过滤的 ESCU 检测(统计偏差类,与 BA 服务思路同类);
  - GitHub `splunk/security_content` 的 detections/ 目录(约 1,700+ 条 SPL 检测,含 MITRE 映射,可直接对标)。

### 10.4 检测管理

- **三态开关(Content Management 中)**:
  - `Turn on in risk index`:事件写入 risk index,参与 RBA;
  - `Turn on in test index (ba_test)`:**默认状态**——BA 检测事件默认进 ba_test;
  - `Turn off`:任何索引都不产生事件。
- **ba_test 沙箱设计**(官方原文要点):BA 检测事件可先转发到 test index `ba_test` 而非 risk index,以便**预览本会写入 risk index 的事件、不污染 RBA 框架、降低告警量**;ba_test 充当"实验沙箱",用于识别真正有意义的检测后再放入生产。可用 **Risk analysis 仪表盘**同时可视化 ba_test 与 risk index 中的事件。
- **检测详情页**还能看到检测版本/日期/关联故事/所需数据/框架映射/SPL(见 10.3)。
- **模块化输入(modular inputs)**:ES 7.1.x/7.2.x 可在 `Settings > Data inputs` 打开 **ES Asset Exporter / ES Identity Exporter**,把资产/身份数据摄取进 BA 服务以 enrich 检测。

### 10.5 Windows 事件日志配置要求

BA 检测**必须**有 **4688、4103、4104** 事件才能生成异常。需在 Windows 侧配置:

**4688(进程创建 + 命令行):**
1. 开启 **Audit Process Creation**:`Computer Configuration > Policies > Windows Settings > Security Settings > Advanced Audit Configuration > Detailed Tracking > Audit Process Creation`,Success 与 Failure 都勾选;
2. 开启 **Include command line in process creation events**:`Computer Configuration > Policies > Administrative Templates > System > Audit Process Creation`,设为启用。
- 官方提供 Ansible 自动化脚本:写注册表 `HKLM:\Software\Microsoft\Windows\CurrentVersion\Policies\System\Audit` 下 `ProcessCreationIncludeCmdLine_Enabled = 1`(dword),并用 `win_audit_policy_system` 将 `Process Creation` 子类审计设为 `success, failure`。

**4103 / 4104(PowerShell 日志):**
- 在 `Administrative Templates > Windows Components > Windows PowerShell` 下依次启用:
  1. **Turn on Script Execution**(选择执行策略,如 Allow all scripts);
  2. **Turn on Module Logging**;
  3. **Turn on PowerShell Script Block Logging**;
  4. **Turn on PowerShell Transcription**。
- Ansible 脚本:注册表 `HKLM:\Software\Policies\Microsoft\Windows\PowerShell\ScriptBlockLogging` 下 `EnableScriptBlockLogging = 1`、`EnableScriptBlockInvocationLogging = 1`,然后重启。
